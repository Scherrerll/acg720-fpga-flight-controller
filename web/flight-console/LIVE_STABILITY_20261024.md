# 官网响应、误断开与空值处理

仅修改 HTTP 转发和网页，FPGA、串口接收器、原始日志不变。当前官网 https://gmflylog.com/ ，发布到原 EdgeOne 项目，部署号 `dp9z2uxti3kg`。

## 排查证据

- 本地接收页面约 200ms 轮询；官网多经过 1Hz 发布、云存储读取和公网请求。修改前 12 轮同时采样中，源端和本地转发均正常，官网单次请求约 1.1–1.4 秒，三轴数值也完整；没有在这组采样中复现用户报告的空姿态。
- 已确认 B0B0 的“待机”“自稳 + 高度控制”等上报字符串未被旧模式白名单接受，导致网页模式栏显示“—”。现已映射为明确的有限模式码，未知字符串仍不外传。
- 页面原先把完整请求 RTT 同时用于数据年龄和连接判定。已用测试复现：成功收到的慢响应可能被当作断开；过期快照也会暂停已接收的真实缓冲历史。
- 空/不完整历史姿态可覆盖当前读数。现已用应用测试覆盖：当前有效姿态与曲线缓冲独立；缺一轴时保留同一帧的完整 Roll/Pitch 对，不用另一时刻的 Pitch 拼出新姿态。
- 转发端原先反复新建 HTTPS 连接。相同健康接口的实测中，首次连接约 931ms，复用后的三次为 387/364/376ms。此数值仅说明这次接口测量，不代表所有官网请求耗时。

## 修改

1. 默认开启“姿态即时”，仪表直接跟随最新接收姿态；“曲线平滑”独立保留约 4 秒缓冲。关闭“姿态即时”可继续让姿态随曲线回放。
2. 保留最后有效 Roll/Pitch 对与相对航向，显示数据年龄及保留状态；第一次尚无有效姿态时显示等待，不造零值。固件/启动序号变化会清除前一来源姿态。
3. 数据过期与连接中断分别显示。没有放宽源端 TTL 或公网 5 秒 freshness 门限；过期数据不会变成 fresh。来源/时间有效的已接收历史可继续回放，真正断流仍提示并停止向最新历史点之后播放。
4. 本地 GM-FLY 页面按 200ms 轮询，官网维持 1Hz 请求节奏，始终只有一个实时请求在途。
5. 实时发布和对时复用已验证 TLS 的 HTTPS 连接，继续使用现有系统代理。特殊/认证代理仍回到原 urllib 路径。失效的已复用连接最多重试一次；跨来源请求、重定向、超大响应均拒绝。日志传输继续用独立路径，避免大日志占住实时连接。
6. 补齐待机、自稳+高度、光流+高度和手动油门接管模式映射。姿态、模式、遥控/PWM 与 freshness 状态没有被伪造成新的当前值。

## 验证

41 项 Node 测试、33 项 Python 测试通过，覆盖慢响应、缓存空值、启动历史回退、源失效、来源变化、模式白名单、单请求轮询、TLS 连接复用、代理回退、重试/大小上限。构建成功。

正式发布后连续约一分钟，每条链路各采样 36 次：

| 链路 | 平均数据年龄 | 最大数据年龄 | 请求错误/过期/断开/空姿态 |
| --- | --- | --- | --- |
| 串口接收源 HTTP | 106.9ms | 246.9ms | 均为 0 |
| 本地 GM-FLY 转发 | 246.9ms | 459.0ms | 均为 0 |
| 官网 API | 1890.8ms | 3216.1ms | 均为 0 |

三条链路均取得 36 个不同序号。该短时观察不能保证任意网络永不断流，也不是飞行控制验证。本地浏览器已确认姿态数值、数据年龄和“待机/模式请求”显示；公网浏览器检查超时，因此线上通过 HTML、app.js、styles.css 和三个模块逐文件 SHA-256 与构建一致、正确 MIME/no-store 响应及真实 API 连续采样核验。
